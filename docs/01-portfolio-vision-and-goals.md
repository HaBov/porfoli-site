## 2. Purpose of This Document

Этот документ определяет стратегическое направление персонального сайта-портфолио Khasandjon Babadzhanov.

Он фиксирует:

- для кого создается сайт;
- какую профессиональную позицию он должен формировать;
- какие навыки и результаты необходимо доказать;
- как показывать закрытые коммерческие проекты;
- какие действия ожидаются от посетителя;
- что входит в первую версию сайта;
- по каким критериям будет оцениваться качество результата.

Все последующие решения по структуре, дизайну, контенту, технологиям и разработке должны соответствовать этому документу.

## 3. Project Context

Khasandjon Babadzhanov развивает карьеру Software Developer с основным фокусом на backend-разработке, бизнес-приложениях, интеграциях и автоматизации.

Основной технический опыт включает:

- Python;
- FastAPI;
- Django;
- PostgreSQL;
- SQLAlchemy ORM;
- Redis;
- Celery;
- Docker;
- Linux;
- REST APIs;
- TypeScript;
- Cloudflare Workers;
- интеграции с внешними сервисами;
- разработку внутренних бизнес-систем;
- тестирование и production deployment.

Значительная часть сильнейших проектов была реализована внутри компании и не может быть полностью опубликована в GitHub из-за конфиденциальности, безопасности и принадлежности исходного кода работодателю.

Поэтому портфолио должно заменить прямой доступ к закрытым репозиториям и показать инженерные навыки через:

- подробные project case studies;
- архитектурные схемы;
- обезличенные code samples;
- объяснение технических решений;
- описание личного вклада;
- демонстрационные API;
- результаты и измеримые метрики;
- screenshots без конфиденциальных данных;
- описание тестирования и deployment-процесса.

## 4. Product Vision

Создать профессиональное техническое портфолио, которое показывает Khasandjon не как кандидата с набором перечисленных технологий, а как Software Developer, способного:

- понять бизнес-проблему;
- преобразовать требования в техническое решение;
- спроектировать backend-архитектуру;
- разработать и интегрировать API;
- работать с реляционными базами данных;
- автоматизировать операционные процессы;
- тестировать критические workflows;
- развертывать приложения на Linux-серверах;
- поддерживать систему после запуска;
- объяснять инженерные решения понятным языком.

Сайт должен создавать у рекрутера или инженера ощущение, что кандидат уже работал с реальными системами, пользователями, ограничениями и производственными задачами.

Основное профессиональное сообщение сайта:

> Software Developer building reliable backend systems, business applications, integrations, and automation with Python, PostgreSQL, TypeScript, Docker, and Linux.

> Backend-focused developer with experience taking internal products from business requirements to deployed systems used by operational teams.

Эти формулировки должны направлять содержание главной страницы, раздела About, описаний проектов и профессионального опыта.

## 6. Primary Goals

### 6.1. Подтвердить технические навыки

Сайт должен предоставить доказательства владения следующими направлениями:

- Python application development;
- REST API design;
- PostgreSQL и relational data modeling;
- ORM и database migrations;
- authentication и role-based access control;
- background processing;
- integrations и webhooks;
- testing;
- Docker;
- Linux deployment;
- TypeScript;
- Git-based development workflow;
- техническая документация;
- анализ и автоматизация бизнес-процессов.

Навык не должен отображаться только в списке технологий. Для важных технологий необходимо показать проект, архитектурное решение или пример кода.

---

### 6.2. Компенсировать отсутствие публичного доступа к коммерческим репозиториям

Портфолио должно честно объяснять, почему production-код некоторых проектов не опубликован.

Вместо закрытого исходного кода необходимо показать:

- самостоятельное описание архитектуры;
- упрощенные и обезличенные реализации;
- фрагменты кода, переписанные специально для портфолио;
- API contracts;
- database models;
- validation logic;
- service-layer patterns;
- permission checks;
- background jobs;
- тестовые сценарии;
- технические trade-offs.

Посетитель должен получить достаточно информации для оценки инженерного мышления без раскрытия интеллектуальной собственности работодателя.

---

### 6.3. Повысить качество откликов на вакансии

Сайт должен использоваться как дополнительный аргумент при подаче на позиции:

- Software Developer;
- Python Developer;
- Backend Developer;
- Junior Backend Developer;
- Junior Software Engineer;
- Full-Stack Developer с backend-фокусом;
- Integration Developer;
- Business Applications Developer;
- Automation Engineer;
- Software Engineering Internship.

Основной приоритет — вакансии, связанные с Python, backend-разработкой, бизнес-приложениями, PostgreSQL, API и внутренними системами.

---

### 6.4. Поддержать международный поиск работы

Сайт должен быть понятен международным рекрутерам и инженерным командам.

Поэтому:

- основной язык интерфейса и контента — английский;
- формулировки должны быть профессиональными и естественными;
- даты и названия разделов должны соответствовать международному формату;
- сайт должен ясно показывать текущую локацию;
- должна быть указана готовность к relocation;
- контактные данные должны быть доступны без регистрации;
- резюме должно скачиваться в PDF;
- сайт должен корректно работать на мобильных устройствах.

---

### 6.5. Продемонстрировать способность завершать проекты

Портфолио само должно стать доказательством инженерной дисциплины.

Посетитель должен видеть, что кандидат способен:

- определить scope;
- создать дизайн-систему;
- структурировать контент;
- разработать frontend;
- подключить backend demo;
- контейнеризировать приложение;
- настроить production deployment;
- обеспечить HTTPS;
- провести тестирование;
- поддерживать документацию.

Сайт не должен выглядеть как незавершенный шаблон или набор несвязанных блоков.

## 7. Target Audience

### 7.1. Technical Recruiters

Рекрутер должен быстро понять:

- какую позицию ищет кандидат;
- какой у него основной стек;
- есть ли практический опыт разработки;
- какие системы он создавал;
- какие результаты достигнуты;
- доступен ли кандидат для relocation или remote work;
- где скачать резюме;
- как связаться с кандидатом.

Целевое время для получения основного представления — до 60 секунд.

Hiring manager должен увидеть:

- ответственность за законченные функции;

- понимание reliability и testing;
- измеримый бизнес-эффект проектов;
- реалистичное понимание собственного уровня.

Технический специалист должен иметь возможность оценить:

- структуру кода;
- разделение ответственности;

- API design;
- validation;
- error handling;
- authentication и authorization;
- background processing;
- тестируемость;
- архитектурные trade-offs;
- качество технических объяснений.

### 7.4. Companies Offering Relocation

Компания должна быстро найти:

- текущую страну проживания;
- готовность к переезду;
- уровень английского;
- международный или удаленный опыт;
- технический профиль;
- актуальное резюме;
- контактную информацию.

## 8. Desired Visitor Perception

После просмотра сайта посетитель должен сформировать следующие выводы:

1. Кандидат имеет реальный практический опыт, а не только учебные проекты.
2. Кандидат способен создавать backend-системы для бизнес-процессов.
3. Кандидат понимает полный жизненный цикл функции: требования, разработка, тестирование, deployment и поддержка.
4. Кандидат умеет работать с Python, PostgreSQL, API, Docker и Linux.
5. Кандидат может объяснять сложные технические решения структурированно и понятно.
6. Отсутствие публичного production-репозитория связано с конфиденциальностью, а не с отсутствием кода.
7. Кандидат честно показывает свой уровень и не приписывает себе неподтвержденные технологии.
8. Кандидат способен быстро осваивать новый framework или stack.
9. С кандидатом стоит провести техническое интервью.

**Software Developer with a backend focus**

- не ограничивать кандидата только FastAPI;
- соответствовать вакансиям Software Developer;

### 9.2. Supporting Specializations

На сайте могут использоваться следующие дополнительные направления:

- Business Applications;
- API Integrations;

## 12. Content Principles

### 12.1. Evidence Over Claims

Вместо:

> Experienced with scalable backend systems.

Использовать:

> Built an archival workflow processing 90,000–150,000 recordings per 90-day cycle.

Каждое сильное утверждение должно поддерживаться:

- проектом;
- code sample;
- diagram;
- screenshot;
- метрикой;
- техническим объяснением.

---

### 12.2. Clarity Over Complexity

Контент должен быть понятен одновременно рекрутеру и инженеру.

Первый уровень страницы проекта должен объяснять:

- проблему;
- решение;
- роль;
- результат.

Более глубокие разделы должны раскрывать:

- архитектуру;
- код;
- тестирование;
- trade-offs.

---

### 12.3. Honesty Over Keyword Density

Нельзя добавлять технологии только ради соответствия вакансии.

Если технология изучается, но еще не использовалась в проекте, она может быть обозначена отдельно как learning area, но не как production skill.

---

### 12.4. Business Context With Technical Depth

Каждый case study должен соединять:

- бизнес-проблему;
- техническое решение;
- личный вклад;
- результат.

Нельзя ограничиваться только описанием интерфейса или списка технологий.

---

### 12.5. Scannable Content

Страницы должны поддерживать быстрое чтение:

- короткие абзацы;
- понятные заголовки;
- выделенные метрики;
- technology badges;
- списки ключевых решений;
- визуальные architecture diagrams;
- компактные code samples.

## 18. Security and Confidentiality Goals

Сайт не должен создавать риски для текущего или предыдущих работодателей.

Запрещено публиковать:

- API keys;
- passwords;
- access tokens;
- private certificates;
- внутренние IP-адреса;
- закрытые домены;
- персональные данные сотрудников;
- реальные записи звонков;
- database dumps;
- конфиденциальные бизнес-правила;
- корпоративный исходный код без разрешения;
- внутренние security configurations;
- названия клиентов без согласования.

Все code samples из закрытых проектов должны быть:

- переписаны;
- упрощены;
- обезличены;

## 25. Risks

### 25.1. Сайт может выглядеть как frontend showcase

**Риск:** сложные эффекты отвлекут от backend-компетенций.

**Решение:** использовать сдержанный интерфейс, а основное внимание направить на архитектуру, код и результаты.

### 25.2. Недостаточно доказательств личного вклада

**Риск:** проекты могут восприниматься как работа всей команды без понятной роли кандидата.

**Решение:** в каждом case study добавить раздел `My Role and Contributions`.

### 25.3. Code samples могут выглядеть искусственно

**Риск:** слишком упрощенный код не покажет production thinking.

**Решение:** сопровождать каждый пример контекстом, ограничениями, тестами и объяснением design decisions.

### 25.4. Возможное раскрытие конфиденциальных данных

**Риск:** screenshots или код могут содержать внутреннюю информацию.

**Решение:** обязательная security review перед публикацией каждого материала.

### 25.5. Слишком большой scope

**Риск:** попытка сразу создать все страницы и demos задержит запуск.

**Решение:** сначала завершить Home, Projects, четыре case studies, Code Samples, About и Contact. Остальное добавлять итеративно.

### 25.6. Несоответствие между портфолио и реальным уровнем

**Риск:** чрезмерно рекламные формулировки вызовут сомнения на интервью.

**Решение:** использовать только подтвержденный опыт и четко отделять production experience от learning projects.

## 26. Decision Principles

При конфликте между несколькими решениями использовать следующие приоритеты:

1. Достоверность важнее впечатляющей формулировки.
2. Доказательство важнее списка технологий.
3. Читаемость важнее визуального эффекта.
4. Technical depth важнее количества проектов.
5. Безопасность важнее полноты раскрытия проекта.
6. Быстрый production launch важнее идеальной первой версии.
7. Простая архитектура важнее ненужной сложности.
8. Реальный business impact важнее декоративных metrics.
9. Mobile usability важнее desktop-only композиции.
10. Поддерживаемость важнее краткосрочного визуального результата.
