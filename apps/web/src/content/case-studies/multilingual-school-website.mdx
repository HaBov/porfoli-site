<CaseStudySection

  eyebrow="Overview"
  title="Executive Summary"
>
  The Multilingual School Website is a production Django application used to publish school information, admissions documents, educational materials, committee information, and other public content in multiple languages.

  I maintained and extended the existing application by updating Django models, creating and applying database migrations, improving administrative workflows, updating translated fields, managing public documents, and supporting the Linux production deployment.

  The work focused on safely evolving a live website without interrupting the public service or exposing private administration and infrastructure details.
</CaseStudySection>

<CaseStudySection
  id="problem"
  eyebrow="Business problem"
  title="Maintaining Structured Multilingual Content"
>
  The website needed to support public information that changes over time and must remain manageable by administrators without editing source files.

  Several content areas required new fields, longer values, translated labels, document uploads, and improved administration. These changes had to be introduced while preserving existing production data and keeping the public website available.

  The main challenge was therefore not creating a new static website. It was safely evolving an existing database-driven Django application.
</CaseStudySection>

<CaseStudySection
  id="data-model"
  eyebrow="Persistence"
  title="Content and Translation Model"
>
  The application stores public website content in Django models instead of hardcoding every section into templates.

  The multilingual layer uses translated model fields so that the same logical record can provide language-specific values.

  Relevant modeling patterns include:

  - One database record representing one public content item.
  - Separate translated values for supported languages.
  - Administrative ordering and visibility fields.
  - File and document references stored with content records.
  - Text fields for values that may exceed ordinary URL-field limits.
  - Migration-controlled schema evolution.
  - PostgreSQL as the authoritative production data source.

  Migrations `0003`, `0004`, and `0005` were applied as part of the production changes represented in this case study.
</CaseStudySection>

<CaseStudySection
  id="challenges"
  eyebrow="Implementation challenges"
  title="Challenges"
>
  One challenge was changing model fields without losing existing production content. A schema change that is simple in development can affect real records, administration forms, templates, and translations in production.

  Another challenge was supporting values such as long external links. Fields originally designed for shorter URLs had to be changed carefully while preserving existing values and template compatibility.

  Multilingual content also requires synchronization between model definitions, translation configuration, message files, compiled translations, administration, and public rendering.

  The safest approach was to make focused changes, generate explicit migrations, verify the production database, and inspect the affected pages after every deployment.
</CaseStudySection>

<CaseStudySection
  id="lessons"
  eyebrow="Reflection"
  title="Lessons Learned"
>
  Maintaining an existing production system requires different judgment from starting a new project.

  The most important lessons were:

  - Understand current data before changing models.
  - Treat migrations as production code.
  - Separate public content from private administration.
  - Verify translations at both model and interface levels.
  - Prefer focused changes over unnecessary rewrites.
  - Confirm deployment results on the real public route.
  - Avoid claiming metrics that have not been measured.
</CaseStudySection>
