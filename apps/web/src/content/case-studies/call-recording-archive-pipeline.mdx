<CaseStudySection
  id="executive-summary"
  eyebrow="Overview"
  title="Executive Summary"
>
  <p>
    The Call Recording Archive Pipeline is an operational
    integration workflow that transfers high-volume call
    recordings from a communications platform to long-term cloud
    storage.
  </p>

<p>
  The workflow retrieves recording metadata through paginated API requests, applies eligibility
  rules, prevents duplicate uploads, downloads recording files, stores them in an organized
  destination structure, and produces operational reports for review.
</p>

  <p>
    I implemented the API integration, pagination, token refresh,
    filtering, batching, retry behavior, rate-limit handling,
    duplicate detection, storage organization, and reporting
    logic.
  </p>
</CaseStudySection>

<CaseStudySection
  id="problem"
  eyebrow="Business problem"
  title="Retention Was Shorter Than the Operational Requirement"
>
  <p>
    The source communications platform retained recordings for a
    limited period, while operational and compliance-related
    workflows required access to historical files for longer.
  </p>

<p>
  Manual exporting was not practical at the required volume. The process involved multiple accounts,
  paginated API responses, expiring access tokens, download operations, storage organization, and
  the possibility of interrupted or partially completed runs.
</p>

  <p>
    A reliable workflow needed to identify eligible recordings,
    transfer them safely, avoid creating duplicates, and leave
    enough reporting information to understand what happened
    during each run.
  </p>
</CaseStudySection>

  id="business-context"

<CaseStudySection
  id="challenges"
  eyebrow="Trade-offs"
  title="Challenges"
>
  <p>
    <strong>Authentication during long runs.</strong> An access
    token could expire after processing had already started. The
    integration needed to refresh authentication and retry the
    interrupted operation safely.
  </p>

<p>
  <strong>API rate limits.</strong> Processing volume made request pacing important. Temporary
  limits needed cooldown and retry behavior rather than immediate permanent failure.
</p>

<p>
  <strong>Partial failure.</strong> A failed file should be recorded without discarding the
  successful work already completed during the same cycle.
</p>

<p>
  <strong>Duplicate prevention.</strong> Repeated runs needed to recognize previously archived files
  and avoid unnecessary transfers.
</p>

<p>
  <strong>Filename safety.</strong> Source metadata could contain characters or information
  unsuitable for a destination filename.
</p>

  <p>
    <strong>Sensitive metadata.</strong> Logs and reports could
    contain telephone numbers, call identifiers, account
    identifiers, and storage references. Public examples require
    complete replacement rather than visual redaction alone.
  </p>
</CaseStudySection>

<CaseStudySection
  id="lessons"
  eyebrow="Reflection"
  title="Lessons Learned"
>
  <ul>
    <li>
      External API iteration should be isolated from business
      processing logic.
    </li>

    <li>
      Retry behavior must distinguish temporary failures from
      permanent validation problems.
    </li>

    <li>
      Idempotency is necessary for operational workflows that may
      be rerun.
    </li>

    <li>
      Bounded concurrency is safer than treating parallelism as an
      unlimited performance improvement.
    </li>

    <li>
      A run report is part of the product, not only a debugging
      artifact.
    </li>

    <li>
      Credentials and sensitive identifiers require a review
      process before code or logs leave the production
      environment.
    </li>

  </ul>
</CaseStudySection>
