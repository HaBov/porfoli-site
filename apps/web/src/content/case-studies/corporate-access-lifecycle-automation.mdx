<CaseStudySection
  id="executive-summary"
  eyebrow="Overview"
  title="Executive Summary"
>
  <p>
    Corporate Access Lifecycle Automation is an internal workflow
    for managing employee access across a large number of
    corporate communication groups.
  </p>

<p>
  The system connects employee lifecycle events with group membership operations. It helps identify
  which access should be granted, retained, reviewed, or removed when an employee joins, changes
  responsibilities, becomes inactive, or leaves the organization.
</p>

  <p>
    I designed and implemented the automation logic, Telegram API
    integration, batch processing, membership checks, rate-limit
    handling, operation reporting, and failure investigation.
  </p>
</CaseStudySection>

<CaseStudySection
  id="problem"
  eyebrow="Business problem"
  title="Access Was Distributed Across Too Many Groups"
>
  <p>
    Corporate communication was distributed across a large
    collection of groups used by different teams, departments,
    operations, and responsibilities.
  </p>

<p>
  Managing access manually created several risks. New employees could miss required groups,
  transferred employees could retain access that was no longer relevant, and former employees could
  remain in groups after their operational relationship ended.
</p>

  <p>
    The challenge was not only adding or removing one user. The
    workflow needed to compare expected access with actual
    membership across approximately 1,500 groups while respecting
    external API limits and partial failures.
  </p>
</CaseStudySection>

  eyebrow="Processing state"
  title="Access Operation Model"

    model rather than the real employee and group structures.

<p>A generalized operation contains:</p>

  <ul>
    <li>A synthetic employee identifier.</li>

    <li>A lifecycle event type.</li>

    <li>A synthetic group identifier.</li>

    <li>An expected membership state.</li>

    <li>An observed membership state.</li>

    <li>A planned action such as add, remove, retain, or review.</li>

    <li>An approval or execution state.</li>

    <li>An attempt count.</li>

    <li>A generalized failure category.</li>

    <li>A completion timestamp.</li>

  <p>

    from the external API call that attempts to apply it.

<CaseStudySection
  id="technical-decisions"
  eyebrow="Engineering choices"
  title="Technical Decisions"
>
  <div className="grid gap-6">
    <TechnicalDecision
      title="Reconciliation instead of isolated add and remove commands"
      context="Employee access could change over time, and isolated commands did not provide a reliable view of whether actual membership matched the intended state."
      optionsConsidered={[
        "Run individual add or remove commands manually",
        "Apply predefined group lists without checking current state",
        "Compare expected access with observed membership before planning operations",
      ]}
      selectedApproach="A reconciliation workflow that calculates the difference between expected and actual access."
      reasoning="Reconciliation makes missing access, unnecessary access, and already-correct access visible before external operations are applied."
      tradeoffs={[
        "Current membership data may be incomplete when API permissions are limited.",
        "Expected-access rules must remain synchronized with operational policy.",
        "Large comparisons require efficient batching and reporting.",
      ]}
    />

    <TechnicalDecision
      title="Separate operation planning from operation execution"
      context="An incorrect access removal could affect active operational communication."
      optionsConsidered={[
        "Apply API operations immediately after calculating access",
        "Produce an operation plan before applying changes",
      ]}
      selectedApproach="Create explicit planned operations and execute only approved or eligible actions."
      reasoning="Separating planning from execution creates a review boundary and makes high-impact changes easier to inspect."
      tradeoffs={[
        "The workflow contains additional states.",
        "Plans can become stale when membership changes before execution.",
        "Review adds time to urgent access changes.",
      ]}
    />

    <TechnicalDecision
      title="Bounded batches with rate-limit handling"
      context="The workflow needed to process a large group inventory through an external API with request limits."
      optionsConsidered={[
        "Send all operations concurrently",
        "Process every operation strictly one at a time",
        "Use bounded batches with cooldown and retry behavior",
      ]}
      selectedApproach="Controlled batches with limited concurrency, retry rules, and cooldown periods."
      reasoning="This approach balances processing time with external API stability and makes failures easier to isolate."
      tradeoffs={[
        "Batch size requires operational tuning.",
        "Temporary failures can extend total processing time.",
        "Concurrent result aggregation requires consistent state handling.",
      ]}
    />

  </div>
</CaseStudySection>

<CaseStudySection
  id="challenges"
  eyebrow="Trade-offs"
  title="Challenges"
>
  <p>
    <strong>Large access surface.</strong> Approximately 1,500
    groups created a large comparison and operation space. The
    workflow needed batching and clear summaries rather than
    unstructured per-group output.
  </p>

<p>
  <strong>External permissions.</strong> The automation could only perform actions allowed by its
  administrative access in each group.
</p>

<p>
  <strong>Identity resolution.</strong> Employee records and Telegram identities could not always be
  matched through one stable field.
</p>

<p>
  <strong>Rate limits.</strong> High-volume membership operations needed controlled execution and
  cooldown behavior.
</p>

<p>
  <strong>Partial failure.</strong> One inaccessible group or invalid user should not discard the
  successfully completed operations in the same batch.
</p>

  <p>
    <strong>High-impact removals.</strong> Removing the wrong user
    from operational groups could interrupt work, so planning,
    review, and reporting were important safeguards.
  </p>
</CaseStudySection>

<CaseStudySection
  id="lessons"
  eyebrow="Reflection"
  title="Lessons Learned"
>
  <ul>
    <li>
      Access management is a state-reconciliation problem, not
      only a collection of API commands.
    </li>

    <li>
      Planning and execution should be separated for high-impact
      operations.
    </li>

    <li>
      External administrative permissions must be treated as part
      of the application state.
    </li>

    <li>
      Partial failure needs an explicit result model.
    </li>

    <li>
      Rate-limit handling should be built into the operation
      executor rather than added after failures appear.
    </li>

    <li>
      Operational reports should distinguish no-op, skipped,
      restricted, successful, and failed actions.
    </li>

    <li>
      Public access-control examples require complete fictional
      identities and group structures.
    </li>

  </ul>
</CaseStudySection>
