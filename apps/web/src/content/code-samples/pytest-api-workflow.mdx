  title="Context"
>
    A business workflow test should prove more than a
    response status. It should validate the public API
    contract, the database state created by the request,
    and any side effect that is part of the operation.

</CodeSampleSection>

<CodeSampleSection
  id="problem"
  eyebrow="Coverage gap"
  title="Problem"
>
    Tests that assert only <code>201 Created</code> can
    pass while the wrong lifecycle state is stored, an
    audit event is missing, or an unauthorized role
    reaches the service.

    A useful workflow test checks the complete path at
    the level where regressions matter.

</CodeSampleSection>

  <ol>
    <li>
      Fixtures create a real department and authenticated
      role context.
    </li>

      would send.
    </li>

      The response schema and generated identifier are

    </li>

      The test queries the database through a separate
      assertion path.
    </li>

    <li>
      The audit endpoint confirms that the side effect is
      publicly observable.
    </li>

    <li>
      A separate role fixture verifies the authorization
      boundary.
    </li>

<CodeSampleSection
  id="design-principles"
  eyebrow="Engineering choices"
  title="Design Principles"
>
  <ul>
    <li>
      <strong>Behavior over implementation:</strong>
      assertions focus on outcomes, not private method
      calls.
    </li>

    <li>
      <strong>Real boundaries:</strong> the test exercises
      routing, validation, authorization, service logic,
      and persistence.
    </li>

    <li>
      <strong>Deterministic data:</strong> reserved
      example domains and fixed dates avoid external
      dependencies.
    </li>

    <li>
      <strong>Independent verification:</strong> database
      assertions do not reuse the response object.
    </li>

  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="error-handling"
  eyebrow="Failure visibility"
  title="Error Handling"
>
    Negative tests should assert the stable application
    error code rather than a full human message.

    This allows wording to improve without weakening the
    contract. Unexpected stack traces must never appear in
    the response body during tests or production.

</CodeSampleSection>

<CodeSampleSection
  id="trade-offs"
  eyebrow="Limits"
  title="Trade-offs"
>
    Full workflow tests are slower than unit tests and
    require reliable fixture isolation.

    They should cover critical paths, while smaller
    service and repository tests provide faster feedback
    for edge cases. A large suite composed only of
    end-to-end tests becomes expensive to maintain.

</CodeSampleSection>

<CodeSampleSection
  id="production-considerations"
  eyebrow="Operational readiness"
  title="Production Considerations"
>
  <ul>
    <li>
      Run tests against a disposable database, never a
      copied production dataset.
    </li>

    <li>
      Reset transactions or schemas between tests.
    </li>

    <li>
      Keep authentication fixtures explicit by role and
      permission.
    </li>

    <li>
      Add smoke tests for deployment-critical endpoints.
    </li>

    <li>
      Track flaky tests as defects rather than rerunning
      until green.
    </li>

  </ul>
</CodeSampleSection>
