<CodeSampleSection

  eyebrow="Authorization"
  title="Context"
>
  <p>
    A modular API may contain dozens of routes that need
    the same authorization behavior. Putting permission
    checks directly inside every route creates
    inconsistent status codes and makes it easy to forget
    a check during later development.
  </p>

  <p>
    This example demonstrates a dependency factory that
    converts a permission code into a reusable FastAPI
    dependency and returns an actor whose authorization
    has already been verified.
  </p>
</CodeSampleSection>

<CodeSampleSection
  id="problem"
  eyebrow="Risk"
  title="Problem"
>
  <ul>
    <li>
      Inline role checks couple routes to the current
      permission model.
    </li>

    <li>
      Checking only a role name does not express the
      capability required by the operation.
    </li>

    <li>
      Different modules may return different errors for
      the same denial.
    </li>

    <li>
      A missing check can expose a sensitive mutation.
    </li>
  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="how-it-works"
  eyebrow="Request path"
  title="How It Works"
>
  <ol>
    <li>
      The authentication dependency resolves the actor
      and tenant context.
    </li>

    <li>
      The permission dependency asks the service for one
      explicit capability.
    </li>

    <li>
      A failed check returns a consistent 403 response
      before route logic executes.
    </li>

    <li>
      A successful check returns a typed actor carrying
      the granted permission.
    </li>

    <li>
      The route remains focused on the application
      operation.
    </li>
  </ol>
</CodeSampleSection>

<CodeSampleSection
  id="design-principles"
  eyebrow="Engineering choices"
  title="Design Principles"
>
  <ul>
    <li>
      <strong>Permission over role:</strong> routes
      declare capabilities, not organizational labels.
    </li>

    <li>
      <strong>Default deny:</strong> an operation runs
      only after an explicit successful check.
    </li>

    <li>
      <strong>Reusable boundary:</strong> one dependency
      is shared across multiple API modules.
    </li>

    <li>
      <strong>Tenant awareness:</strong> permission
      resolution includes the current tenant boundary.
    </li>

    <li>
      <strong>Test visibility:</strong> the required
      permission appears in the generic denial response.
    </li>
  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="error-handling"
  eyebrow="Denial model"
  title="Error Handling"
>
  <p>
    Authentication failures and authorization failures
    remain distinct. Missing or invalid credentials
    should produce 401, while a valid actor without the
    required capability receives 403.
  </p>

  <p>
    The response exposes a generic permission code for
    debugging and testing, but it does not reveal the
    internal role matrix, assignment structure, or
    database implementation.
  </p>
</CodeSampleSection>

<CodeSampleSection
  id="trade-offs"
  eyebrow="Limits"
  title="Trade-offs"
>
  <p>
    Resolving permissions for every request can add
    database work. A production system may cache an
    actor's effective permission set for a limited
    period, but cache invalidation must follow role and
    assignment changes.
  </p>

  <p>
    Permission checks at the route boundary also do not
    replace object-level authorization. A user may have
    permission to update employees generally while still
    being restricted to a specific department or tenant.
  </p>
</CodeSampleSection>

<CodeSampleSection
  id="production-considerations"
  eyebrow="Operational readiness"
  title="Production Considerations"
>
  <ul>
    <li>
      Register permission codes centrally to prevent
      spelling drift.
    </li>

    <li>
      Log authorization denials without logging access
      tokens or full request payloads.
    </li>

    <li>
      Invalidate cached permissions after role,
      membership, or assignment changes.
    </li>

    <li>
      Test every sensitive mutation endpoint with an
      unauthorized actor.
    </li>

    <li>
      Keep object-level access checks separate from
      global capability checks.
    </li>

    <li>
      Preserve tenant boundaries in every permission
      lookup.
    </li>
  </ul>
</CodeSampleSection>
