<CodeSampleSection
  id="context"
  eyebrow="External integration"
  title="Context"
>
    Export workflows often read a large collection from
    an external API before downloading or archiving
    individual records.


    The provider may return only one page at a time and
    require an opaque continuation token for the next
    request.

</CodeSampleSection>

<CodeSampleSection
  id="problem"
  eyebrow="Integration risk"
  title="Problem"
>
    Pagination logic can silently lose records or loop
    forever when a provider returns an unexpected token.
    Large exports must also respect rate limits and
    temporary server failures.


  <ul>
    <li>
      Consumers should not need to manage page tokens.
    </li>

    <li>
      API responses require validation before use.
    </li>

    <li>
      Rate limits should produce bounded delays.
    </li>

    <li>
      Repeated continuation tokens must stop the export.
    </li>

    <li>
      Client and server errors need different handling.
    </li>
  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="how-it-works"
  eyebrow="Request flow"
  title="How It Works"
>
  <ol>
    <li>
      The consumer requests a date range and iterates over
      records.
    </li>

    <li>
      The client builds parameters for the current page.
    </li>

    <li>
      The response is validated through a typed Pydantic
      model.
    </li>

    <li>
      Records are yielded individually without storing
      the entire export in memory.
    </li>

    <li>
      The continuation token is used for the next page.
    </li>

    <li>
      A repeated token raises an explicit integration
      error.
    </li>

    <li>
      A missing token ends iteration normally.
    </li>
  </ol>
</CodeSampleSection>

<CodeSampleSection
  id="design-principles"
  eyebrow="Engineering choices"
  title="Design Principles"
>
  <ul>
    <li>
      <strong>Streaming interface:</strong> callers
      process one record at a time.
    </li>

    <li>
      <strong>Typed boundary:</strong> unknown JSON is
      validated before entering application logic.
    </li>

    <li>
      <strong>Opaque tokens:</strong> continuation values
      are passed through without interpretation.
    </li>

    <li>
      <strong>Loop protection:</strong> repeated tokens
      fail visibly.
    </li>

    <li>
      <strong>Bounded resilience:</strong> retry behavior
      has a clear maximum.
    </li>
  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="error-handling"
  eyebrow="Failure model"
  title="Error Handling"
>
    A 429 response uses the provider's
    <code>Retry-After</code> header when available.
    Numeric seconds and HTTP-date formats are both
    supported.


    Server errors receive bounded exponential delays.
    Other client errors fail immediately because retrying
    an invalid request would not correct it.


    Authentication tokens and response bodies are not
    included in raised errors.

</CodeSampleSection>

<CodeSampleSection
  id="trade-offs"
  eyebrow="Limits"
  title="Trade-offs"
>
    An async iterator is memory efficient but does not
    automatically provide resumability after the process
    stops.


    For very large exports, the application should
    persist the last successful token or date checkpoint
    outside the iterator.


    Tokens may expire, so a durable export workflow also
    needs a strategy for restarting from a stable
    business cursor.

</CodeSampleSection>

<CodeSampleSection
  id="production-considerations"
  eyebrow="Operational readiness"
  title="Production Considerations"
>
  <ul>
    <li>
      Store access tokens only in a secret manager or
      protected environment variable.
    </li>

    <li>
      Log page counts and record counts without logging
      raw continuation tokens.
    </li>

    <li>
      Persist export checkpoints for long-running jobs.
    </li>

    <li>
      Apply global rate limiting when multiple workers
      share one provider account.
    </li>

    <li>
      Monitor schema validation failures as potential API
      contract changes.
    </li>

    <li>
      Use reserved domains such as
      <code>example.com</code> in tests and public
      documentation.
    </li>
  </ul>
</CodeSampleSection>
