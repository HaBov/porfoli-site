    A backend application typically depends on more than

<CodeSampleSection
  id="problem"
  eyebrow="Deployment boundary"
  title="Problem"
>
    A development Compose file often publishes every
    service port, runs containers as root, writes anywhere
    in the filesystem, and starts services without
    checking readiness.

  <ul>
    <li>
      Databases should not be directly exposed.
    </li>

    <li>
      The application should not run as root.
    </li>

    <li>
      Dependency startup order should use health status,
      not only container creation.
    </li>

    <li>
      Runtime filesystems should be restricted where
      practical.
    </li>

    <li>
      Configuration and secrets should remain outside the
      image.
    </li>

  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="how-it-works"
  eyebrow="Startup flow"
  title="How It Works"
>
  <ol>
    <li>
      The builder stage creates a virtual environment and
      installs pinned dependencies.
    </li>

    <li>
      The runtime image copies only the installed
      environment and application files.
    </li>

    <li>
      PostgreSQL and Redis start on the internal network.
    </li>

    <li>
      The API starts only after both dependencies report
      healthy.
    </li>

    <li>
      Nginx starts only after the API readiness check
      succeeds.
    </li>

    <li>
      External traffic reaches Nginx, while internal
      service ports remain unpublished.
    </li>

  </ol>
</CodeSampleSection>

<CodeSampleSection
  id="design-principles"
  eyebrow="Engineering choices"
  title="Design Principles"
>
  <ul>
    <li>
      <strong>Least exposure:</strong> only the reverse
      proxy publishes a host port.
    </li>

    <li>
      <strong>Non-root runtime:</strong> the application
      process uses a dedicated system user.
    </li>

    <li>
      <strong>Immutable runtime:</strong> application
      containers use a read-only filesystem with limited
      temporary storage.
    </li>

    <li>
      <strong>Health-aware startup:</strong> dependencies
      are checked for readiness before traffic is routed.
    </li>

    <li>
      <strong>Persistent state:</strong> database and
      Redis data use named volumes.
    </li>

  </ul>
</CodeSampleSection>

<CodeSampleSection
  id="error-handling"
  eyebrow="Failure behavior"
  title="Error Handling"
>
    A failed readiness check prevents Nginx from routing
    traffic to an application that cannot reach its
    dependencies.

    Restart policies recover ordinary process failures,
    but they do not replace alerting or investigation of
    repeated crashes.


    Deployment automation should preserve container logs
    and inspect health status before replacing a previous
    healthy release.

</CodeSampleSection>

<CodeSampleSection
  id="trade-offs"
  eyebrow="Limits"
  title="Trade-offs"
>
    Docker Compose is appropriate for a controlled
    single-server deployment, but it does not provide
    multi-node scheduling or automatic high availability.

    A read-only filesystem improves containment but
    requires every writable application path to be
    identified explicitly.


    Health-based dependency ordering improves startup but
    does not guarantee that a dependency remains healthy
    after the application has started.

</CodeSampleSection>

<CodeSampleSection
  id="production-considerations"
  eyebrow="Operational readiness"
  title="Production Considerations"
>
  <ul>
    <li>
      Keep <code>.env.production</code> outside Git and
      restrict its filesystem permissions.
    </li>

    <li>
      Terminate HTTPS through Nginx or a trusted upstream
      load balancer.
    </li>

    <li>
      Back up PostgreSQL independently from the container
      lifecycle.
    </li>

    <li>
      Set CPU and memory limits based on observed usage.
    </li>

    <li>
      Rotate logs and export metrics to external
      monitoring.
    </li>

    <li>
      Pin base images and rebuild regularly for security
      updates.
    </li>

    <li>
      Test database migrations before the application
      receives traffic.
    </li>

  </ul>
</CodeSampleSection>
